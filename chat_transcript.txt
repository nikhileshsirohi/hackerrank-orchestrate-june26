1. Problem Understanding

I first read and understood problem_statement.md myself.

From the problem statement, I identified the main objective:

* Read each claim from dataset/claims.csv.
* Use the claim conversation to understand what damage is being claimed.
* Use the submitted images as the primary source of truth.
* Use user_history.csv only for risk context.
* Use evidence_requirements.csv as the minimum evidence checklist.
* Produce output.csv with exactly the required output columns and allowed values.

I also understood that this challenge is not asking for a web API. It is a batch-processing and prediction-generation task. Therefore, I decided to build a command-line Python pipeline instead of a FastAPI/backend service.

3. Model Choice

I chose GPT-4o because the problem requires image understanding.

I considered whether traditional CNN models such as ResNet50 or VGG16 would be enough, but decided not to use them as the main approach because the task requires more than classification. The system needs to:

* inspect image evidence,
* identify visible damage,
* identify object parts,
* compare image evidence with the user claim,
* decide support/contradiction/insufficient information,
* return structured reasoning in the required schema.

Therefore, I chose GPT-4o with image inputs as the primary reviewer. The API model name is gpt-4o; it behaves as a vision-capable model when image inputs are provided.

5. Pipeline Design

The final solution was organized as:

* src/main.py: runs the final prediction pipeline on dataset/claims.csv.
* src/evaluator.py: runs sample evaluation on dataset/sample_claims.csv.
* src/llm_client.py: sends claim text and images to GPT-4o.
* src/prompts.py: contains system and user prompts.
* src/schemas.py: contains allowed enum values and output validation logic.
* src/utils.py: contains helper functions for CSV reading, image path parsing, image encoding, user history lookup, and evidence requirement lookup.

The pipeline uses one GPT-4o request per claim row.

Each request includes:

* claim object,
* user claim conversation,
* submitted image IDs,
* submitted images,
* matching user history,
* matching evidence requirements,
* allowed enum values,
* strict JSON output schema.

⸻

6. Prompting Strategy

The prompt was designed around the main rule from the problem statement:

Images are the primary source of truth.

The prompt instructs the model that:

* if claimed damage is clearly visible, return supported;
* if the relevant object part is visible but the claimed damage is absent, return contradicted;
* if the relevant part is not visible, the image is unclear, or the wrong object is shown, return not_enough_information;
* user history can add risk flags but must not override image evidence;
* output must use only the allowed enum values;
* output must be valid JSON only.

⸻

7. Validation Strategy

I added post-processing so that the final CSV is always schema-safe.

The code validates and normalizes:

* claim_status
* issue_type
* object_part
* risk_flags
* severity
* supporting_image_ids

Invalid values are replaced with safe fallbacks:

* invalid claim_status -> not_enough_information
* invalid issue_type -> unknown
* invalid object_part -> unknown
* invalid severity -> unknown
* empty risk_flags -> none
* empty supporting_image_ids -> none

This ensures the final output.csv follows the required schema and enum constraints.
